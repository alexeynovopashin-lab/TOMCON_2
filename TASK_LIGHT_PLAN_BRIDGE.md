# Задача: канал «фотограф ↔ студия» для Light Plan

**Кому:** разработчику TOMCOH_OS / TOMCON_2.
**Зачем:** в Light Plan (планировщик света для фотографов) уже работает студия —
своя сущность с адресом, телефоном администратора и длиной рабочего часа, аренда
со своими началом и концом, баннер студийного часа и звонок администратору по
фазе аренды. Всё это сегодня работает **офлайн, без единого сетевого вызова**.
Не хватает одного: «продлить время» — единственного действия, которому нужен
ответ человека на той стороне.

**Что НЕ входит в задачу.** Ни маркетплейса, ни сделок, ни комиссий, ни
ранжирования студий (запрет `90_Roadmap.md §22` Event OS остаётся в силе).
Ни Event OS: обычная студийная съёмка — портрет, предметка, тест — это
топология 1, где события в смысле Event OS не существует вовсе
(`BRIDGE_LIGHT_PLAN.md §9`). Канал прямой.

---

## Что уже есть на этой стороне (по CLAUDE_CONTEXT.md)

- PWA на GitHub Pages, календарь месяц/неделя/день, три зала со своими
  Google-календарями (§6, §13–17).
- Бронь: `{ id, hallId, name, phone, date, start, end, guests, messenger, pay,
  tags, notes, price, googleEventId, googleCalendarId }` (§5).
- Двусторонняя синхронизация с Google Calendar (§24), правило «никогда не
  создавать дубликаты» (§25).
- Cloudflare Worker `tomson-auth`, KV `TOKENS`, endpoints `/login`,
  `/callback`, `/calendar/*` (§10–12, §33).

Ядро есть. Достроить нужно три вещи, и первая — не про Light Plan.

---

## Шаг 1. Закрыть Worker (обязателен до всего остального)

§34 говорит: перед production проверить авторизацию `/calendar/*`, CORS, доступ
к `/token`, защиту от постороннего использования. Там же сказано «не заниматься
security-hardening, пока базовый flow не проверен» — **эта задача отменяет
отсрочку**. Пока Worker обслуживает одного администратора, риск оценён как
приемлемый. Наружный канал к постороннему фотографу этот расчёт отменяет
полностью.

Минимум:

- `/token` не отдаёт access_token наружу (или исчезает);
- CORS не `*`, а список источников: страница Light Plan и сам PWA студии;
- каждый новый endpoint из шагов 2–3 проверяет источник и ключ запроса.

Это тот же вывод, что уже записан в `ROADMAP.md` этого проекта, раздел
«Горизонт: студия в каталоге», пункт «Этап 7, безопасность».

## Шаг 2. Карточка студии — один read-only endpoint

`GET /studio` → JSON одной студии («Томсон»). Light Plan **копирует ответ
снимком** в карточку съёмки и дальше живёт локально: съёмка идёт там, где связи
может не быть, и сторона окон за час не переедет.

```json
{
  "id": "tomson",
  "name": "Томсон",
  "address": "…",
  "lat": 56.4, "lon": 84.9,
  "tel": "+7…",
  "hourMin": 55,
  "halls": [ { "id": "edison", "name": "Эдисон" },
             { "id": "sfera",  "name": "Сфера" },
             { "id": "vegas",  "name": "Вегас" } ]
}
```

`hourMin` — реальная длина оплаченного часа (у Light Plan это поле уже есть и по
нему считается баннер выхода). Полей про брони здесь нет: это справочник.

Опционально, если дёшево: `"windowsAzimuth"` у зала — одно число, азимут окон.
Оно превращает существующий расчёт солнца в Light Plan в ответ «прямого солнца в
этом зале сегодня не будет» без единого нового экрана. Не обязательно для
продления — но это самое дешёвое, что делает карточку студии полезной снаружи.

## Шаг 3. Продление — переговорная пара, а не уведомление

Это не оповещение: у запроса есть ответ и срок, и **молчание означает «нет»**.

**Запрос от фотографа**

```
POST /rent/extend
{ "bookingRef": "…", "minutes": 60, "requestedAt": "2026-09-03T14:52:00+07:00" }
→ { "id": "rq_…", "status": "requested", "answerBy": "2026-09-03T15:00:00+07:00" }
```

`answerBy` — конец оплаченного времени. После него запрос сам становится
`expired`, и Light Plan показывает это как отказ.

**Ответ администратора** — в интерфейсе дня, рядом с самой бронью, а не
отдельным экраном. Подтвердил → бронь продлевается обычным путём правки брони
(и уезжает в Google Calendar тем же механизмом, без создания дубликата, §25).
Отказал → `declined`.

**Проверка ответа**

```
GET /rent/status?id=rq_…
→ { "status": "requested" | "confirmed" | "declined" | "expired",
    "newEnd": "16:00" }
```

**Конфликт с соседней бронью не разрешается молча** — показывается
администратору, как и требует §39 («graceful degradation») и правило проекта
«конфликт показать администратору, а не разрешать молча».

**Чего это не отменяет.** Фотограф, который просто позвонил, должен получить то
же самое. Канал — удобство поверх телефона, а не замена ему. Продление, не
подтверждённое человеком в студии, продлением не является.

## Шаг 4. Связь по номеру: как фотограф опознаётся у студии

Правило задано Алексеем 3 сентября 2026 — он и фотограф, и владелец студии,
поэтому это описание того, как бронь устроена на самом деле, а не догадка.

**Как бронируют.** Студию бронирует **любой участник фотосессии** — клиент или
сам фотограф — и всегда через TOMCOH_OS. Значит у студии **всегда есть номер
телефона того, кто забронировал**. Клиентом при этом может оказаться и фотограф,
и модель.

**Почему это и есть ключ.** У фотографа в Light Plan тоже всегда есть номер
клиента — карточка съёмки без него не живёт. Обе стороны держат один и тот же
номер, просто не знают об этом. **Совпали — связь есть.**

**Матч ищется по набору номеров, а не по одному.** Бронь оформляет то одна
сторона, то другая, и заранее неизвестно, чей номер попал в бронь. Light Plan
шлёт все номера, которые знает про эту съёмку: свой (владелец приложения),
телефон клиента, телефоны пары. Совпадение любого — связь.

```
POST /booking/match
{ "studioId": "tomson",
  "date": "2026-09-03",
  "from": "14:00", "to": "16:00",
  "phones": ["+7…", "+7…"] }

→ { "match": true, "bookingRef": "…", "hallId": "edison",
    "start": "14:00", "end": "16:00" }
→ { "match": false }
```

**Ключ — тот же, что у будущего ID участника.** В Light Plan уже есть
`appId(phone)` — адрес человека, выведенный из мобильного номера. Матч со
студией должен считаться **той же функцией**, а не своей: тогда это не второй
параллельный механизм, а система ID, применённая на шаг раньше, чем появится
Event OS. Поменяется вывод ID — поменяется и матч, одним местом.

**Что при этом честно сказать про приватность.** `appId` сегодня —
не хэш: `"id" + 79234123330`, номер читается прямо в нём. Но и настоящий хэш
телефона тайны бы не сделал: мобильных номеров порядка десяти миллиардов,
сервер перебирает их за минуты, а секретная соль в PWA с открытым исходником
секретом не бывает. Поэтому:

- **хэшировать стоит как гигиену** — от случайного попадания номера в логи,
  дампы трафика и глаза третьей стороны, которая перебирать не станет;
- **настоящая защита — правило, а не математика**, и оно ниже.

**Правило, обязательное к исполнению на стороне студии.** Совпавший номер студии
уже принадлежит: им же оформляли бронь, ничего нового она не узнаёт. Опасны
только **несовпавшие** — их студия не имела и не должна получить.

- `/booking/match` **не сохраняет и не логирует несовпавшие значения** — ни в
  KV, ни в логах Worker, ни в аналитике;
- ответ не раскрывает, какой именно из присланных ключей совпал;
- Light Plan шлёт набор **только по явному действию фотографа** («связать со
  студией»), а не фоном при каждом открытии карточки.

**Не совпали — QR.** Запасной путь, тот же, что и раньше: код в зале даёт
`bookingRef` текущей брони. Нужен ровно тогда, когда бронь оформлена на номер,
которого у фотографа нет.

## Шаг 5. Один ID на обе системы — и учёт клиентов у студии

Решение Алексея, 3 сентября 2026: те же ID должны работать и в TOMCOH_OS, чтобы
у студии была **одна система учёта клиентов** с пометкой сущностей — «фотограф,
есть Light Plan», «фотограф, нет Light Plan», «клиент, есть приложение»,
«клиент, нет приложения».

**Что это даёт студии.** Администратор видит, с кем можно говорить кнопкой, а
кому нужно звонить. Один и тот же человек не заводится дважды: он опознаётся по
ID, а не по тому, как записали имя в прошлый раз.

**Как считать ID.** Той же функцией, что и в Light Plan: из мобильного номера,
который у брони есть всегда. Функция чистая — TOMCOH_OS считает её сам, ничего
ни у кого не спрашивая. Контакт в базе получает поле `personId` рядом с
`phone`.

**Чего из номера НЕ следует — и это главное в этом шаге.** ID вычисляется всегда.
**«Есть приложение» не вычисляется никогда.** Наличие приложения — не свойство
номера, а факт, который либо кто-то сообщил, либо система наблюдала. Пока нет
головного сервера ID (Event OS, `BRIDGE_LIGHT_PLAN.md §1`), справочника «такой
ID существует» не существует, и спрашивать не у кого.

Значит флаг ставится **наблюдением, и ставит его сам себе**:

- пришёл `POST /booking/match` → на той стороне Light Plan → контакт с этим
  номером помечается «фотограф, есть LP», с датой;
- не приходил → состояние остаётся «неизвестно», а не «нет приложения».
  Разница существенная: «нет» — это утверждение, которого система не может
  сделать.

**Роль тоже не выводится из номера.** Что человек фотограф, а не модель, студия
узнаёт из контекста — запрос пришёл из приложения фотографа, — либо от
администратора, который и так отмечает это при оформлении брони. Из четырёх
названных состояний сегодня **наблюдаемы два**: «фотограф, есть LP» и
«неизвестно». Остальные два ставятся рукой администратора и честнее выглядят
как его пометка, а не как вывод системы.

**Клиентская половина ждёт клиентского приложения.** «Клиент, есть приложение» —
про приложение невесты (`BRIDGE_LIGHT_PLAN.md §4`, условно «WedPlan»): замысел,
кода нет. Поле заводить можно, заполнять пока нечем.

**Приватность здесь ничего не меняет.** `personId` выводится из номера обратимо,
то есть хранить его — то же самое, что хранить телефон, а телефон у студии уже
есть. Правило из шага 4 остаётся в силе и в этом шаге: **ID, пришедший в
несовпавшем наборе, не сохраняется** — по нему у студии нет ни брони, ни
телефона, и появиться в базе он не должен.

## Два уровня, и нижний не требует от студии ничего

Это следствие того же правила, и оно важнее самой связи.

| Что указал фотограф | Что получает |
|---|---|
| Только студию (или студию и зал) | **Напоминалка.** Таймер студийного часа и звонок администратору — всё локально, без сети и без участия студии |
| Студия + совпавшая бронь | Связь: **«вызвать админа»** и **«продлить аренду»** кнопками, в том числе в виджете |

Нижний уровень **уже работает** в Light Plan: студия как сущность, аренда со
своими границами, баннер студийного часа и звонок по фазе аренды сделаны
3 сентября 2026 и не требуют от TOMCOH_OS ни строки. Верхний — это то, ради
чего написана эта задача.

Отсюда практический вывод для оценки: если шаги 1–4 отложатся, фотограф ничего
не теряет по сравнению с сегодняшним днём. Функция деградирует до напоминалки,
а не ломается — это ровно §39 (graceful degradation).
