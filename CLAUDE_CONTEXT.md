# 2. Главная идея продукта

Это не обычная CRM и не просто календарь.

Приложение должно быть **быстрым рабочим инструментом администратора фотостудии**.

Типичный сценарий:

1. Клиент звонит или пишет.
2. Администратор быстро открывает календарь.
3. Видит загрузку залов.
4. Выбирает свободный интервал.
5. Создаёт бронь.
6. Указывает клиента, телефон, количество гостей, мессенджер.
7. Указывает статус предоплаты.
8. При необходимости добавляет специальные условия.
9. Приложение формирует готовое сообщение клиенту.
10. Бронь появляется в общем календаре.
11. Google Calendar используется как рабочая система расписания.
12. Приложение остаётся удобным интерфейсом поверх этого расписания.

Главный критерий:

> Администратор должен выполнить типичную операцию максимально быстро и без ощущения работы с тяжёлой CRM.

> эта локальная бронь соответствует вот этому конкретному событию Google Calendar.

# 7. Google Calendar

Это одна из самых важных частей архитектуры.

Предполагалось:

> один Google-аккаунт студии → несколько календарей → каждый зал соответствует отдельному календарю.

Пример:

```text
Google account
│
├── Эдисон
├── Сфера
└── Вегас
```

Google Calendar нужен не только для отображения.

Он должен стать **реальной рабочей системой расписания**, с которой могут работать и другие сотрудники.

Поэтому в перспективе должно быть возможно:

```text
THOMCOH_OS
     ↕
Google Calendar
```

То есть синхронизация должна быть двусторонней.

# 8. Важное правило разработки Google Calendar

Сейчас используется тестовый календарь.

Это сделано специально.

Нельзя во время разработки рисковать настоящими рабочими бронированиями.

Поэтому тестовый календарь нужно сохранять до тех пор, пока полностью не проверены:

- OAuth;
- создание;
- чтение;
- изменение;
- удаление;
- повторная синхронизация;
- дубликаты;
- истечение access token;
- refresh token;
- конфликты;
- повторная загрузка страницы.

Только после успешного тестового цикла можно подключать реальные рабочие календари.

Не воспринимать тестовый Calendar ID как ошибку.

# 11. Cloudflare KV

Создан KV namespace:

```text

```

Он используется для хранения OAuth-токенов.

Worker хранит:


# 12. Google OAuth

Текущий OAuth flow:

```text
PWA
 ↓
Worker /login
 ↓
Google OAuth
 ↓
Google authorization
 ↓
Worker /callback
 ↓
authorization code
 ↓
Google token endpoint
 ↓
access_token + refresh_token
 ↓
KV
 ↓
PWA
```

Client Secret находится в Cloudflare Secret:

```text
CLIENT_SECRET
```

Он НЕ должен попадать:

- в `index.html`;
- в GitHub;
- в README;
- в frontend JavaScript;
- в сообщения пользователю;
- в логи.

# 22. Локальное хранение

Сейчас PWA использует browser storage.

Это сделано намеренно.

На раннем этапе не нужен тяжёлый backend/database только ради локальной работы интерфейса.

Но важно понимать:

```text
localStorage ≠ общая база
```

Если открыть приложение на другом устройстве, локальное состояние автоматически не станет общей базой.

В будущем возможен переход к серверной базе.

Но это не должно делаться просто «потому что так принято».

Сначала должна быть понятна реальная необходимость:

- несколько администраторов;
- несколько устройств;
- история изменений;
- роли;
- аудит;
- централизованные данные.

# 23. Google Calendar и localStorage

Нельзя смешивать эти понятия.

Сейчас:

```text
localStorage
    +
Google Calendar
```

На этапе разработки localStorage может использоваться как локальный cache/state.

Но если Google Calendar является рабочим источником расписания, необходимо постепенно прийти к модели:

```text
Google Calendar
       ↓
sync layer
       ↓
local application state
```

а не:

```text
localStorage
       +
случайная копия Google Calendar
```

# 24. Двусторонняя синхронизация

Это главная текущая техническая задача.

Нужно получить:

```text
PWA → Google
Google → PWA
```

### Создание

```text
PWA
 ↓
Worker
 ↓
Google Calendar API
 ↓
event.id
 ↓
PWA сохраняет googleEventId
```

### Изменение

```text
PWA
 ↓
Worker
 ↓
Google event/{googleEventId}
```

### Удаление

```text
PWA
 ↓
Worker
 ↓
Google event/{googleEventId}
```

### Обратное изменение

Если сотрудник изменил событие непосредственно в Google Calendar:

```text
Google Calendar
 ↓
Worker
 ↓
PWA
```

PWA должен увидеть изменение.

# 34. Текущая особенность / ограничение Worker

На раннем этапе Worker создавался как минимальный OAuth/API proxy.

Поэтому перед production нужно отдельно проверить:

- авторизацию запросов к `/calendar/*`;
- CORS;
- доступ к `/token`, если такой endpoint остаётся;
- защиту от постороннего использования Worker;
- обработку ошибок Google API;
- rate limits;
- refresh token;
- несколько одновременных запросов;
- корректное поведение после истечения access token.

Но не надо заниматься security-hardening до тех пор, пока базовый flow не проверен.

# 35. Порядок дальнейшей работы

Правильный порядок:

## Этап 1 — стабилизировать Google OAuth

Проверить:

```text
/login
→ Google
→ /callback
→ KV
```

## Этап 2 — чтение

Проверить:

```text
Google Calendar
→ Worker
→ PWA
```

## Этап 3 — создание

Сделать:

```text
PWA
→ Worker
→ Google
```

и получить:

```text
googleEventId
```

## Этап 4 — изменение

Проверить изменение того же события.

## Этап 5 — удаление

Проверить удаление.

## Этап 6 — обратная синхронизация

Изменить событие непосредственно в Google Calendar и убедиться, что PWA его видит.

## Этап 7 — конфликты

Определить правила:

```text
PWA изменил
Google изменил
оба изменили
```

## Этап 8 — только после этого

Подключать реальные рабочие календари.

# 39. Важный продуктовый принцип

Проект должен быть полезен даже человеку, который:

- не хочет устанавливать приложение;
- не хочет подключать Google;
- не хочет пользоваться определённым мессенджером;
- просто позвонил администратору.

Например:

```text

локальный интерфейс продолжает работать
```

или:

```text
мессенджер недоступен
      ↓
телефон / копирование сообщения
```

Не делать внешний сервис единственной точкой отказа пользовательского сценария.
